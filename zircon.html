Zircon is a server wrapper and client launcher pair. The server owner defines which mods the server requires — the bill of materials. The client reads it, fetches exactly those mods and modloader, and connects. No forum posts, no mismatched jars, no "which version of Forge again?"

Why this exists

Modpacks break at the door, not on the server

The server is usually the easy part. The friction is everything a player has to do before they ever load in.

// mismatch

Wrong mod, wrong version

Players grab whatever their launcher of choice offers, and half of them don't match what the server is actually running. Nobody finds out until the crash log.

// drift

The pack drifts from the docs

The owner updates a mod, forgets to update the pinned instructions, and now the setup guide is lying to every new player who reads it.

// support load

Support falls on the owner

"Which modloader?" "Where do I put the jar?" "It still doesn't load." Every one of these is a message the server owner didn't sign up to answer.

The resolution path

From server config to loaded world, in three steps

Everything downstream of the bill of materials is automatic. The owner sets it once; every client resolves it the same way.

1

Owner defines the manifest

Through the wrapper's web UI, the server owner lists required mods, pinned versions, and the modloader — the bill of materials for that server.

wrapper · javalin ui
2

Client requests it

On connect, the launcher pulls the current manifest from the server and diffs it against what's already installed locally.

launcher · handshake
3

Client resolves and joins

Missing or outdated mods and the modloader itself are fetched and verified, then the launcher hands off straight into the join.

launcher · fetch + verify
Two applications, one contract

The wrapper writes the manifest. The launcher reads it.

They never need to trust each other's internals — only the bill of materials that passes between them.

01 · runs alongside the server

Server Wrapper

java · javalin
  • Web dashboard for building and editing the bill of materials
  • Wraps server start/stop so the wrapper always has an accurate mod state
  • Serves the manifest to any client that asks, versioned and signed
  • Flags conflicting or missing dependencies before players ever see them
02 · runs on the player's machine

Client Launcher

java · javafx
  • One field: server address. It fetches the rest.
  • Downloads and installs the exact modloader version required
  • Verifies every mod against the manifest before launch
  • Re-checks on every connect, so drift never reaches the player

What the manifest buys you

Built so drift can't happen quietly

◆

Version pinning

Every mod is pinned to an exact version. The client never guesses at "latest."

◆

Checksum verification

Downloaded jars are hashed and checked before they ever touch the mods folder.

◆

Conflict detection

The wrapper flags known incompatibilities while the owner is still editing the list.

◆

Delta downloads

Clients only fetch what changed since their last connect, not the whole pack again.
